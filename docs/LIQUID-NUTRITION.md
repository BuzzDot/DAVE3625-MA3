## Confirmed limitation

The parser required package mass evidence and rejected volume products. Simply accepting those products would also have been wrong: the saved-food model, portion editor and SQL snapshot trigger treated all amounts as grams. Open Food Facts documents normalized `_100g` nutrients as per 100 g **or per 100 ml for liquids**, despite that legacy suffix. `nutrition_data_per` describes how label values were entered and is not sufficient by itself to establish the normalized measurement dimension. See the [OFF nutrition schema](https://openfoodfacts.github.io/documentation/docs/Product-Opener/schemas/schemas/product_nutrition/) and [product quantity/serving schema](https://openfoodfacts.github.io/documentation/docs/Product-Opener/schemas/schemas/product/).

## Mapping and review

- Use normalized `_100g` values as supplied, with explicit `g` or `ml` nutrition basis. Never convert milliliters to grams or infer density from a product name, calorie count or sugar-free claim.
- Require consistent package/serving dimensions from normalized quantity-unit metadata or explicit labeled measurements. Normalize kg/mg within mass and l/dl/cl within volume only. Serving-only volume evidence also requires the provider's beverage taxonomy. Beverage categories alone cannot establish a measurement unit. Reject unsupported, missing or conflicting dimensions and unknown label-entry bases; accept `100g`, `100ml` and measurable `serving` label-entry metadata.
- Only as-sold normalized nutrients are used; prepared/diluted tables and densities are not inferred. Products explicitly marked without nutrition data are rejected. Missing or invalid individual values stay null, including sugars. Explicit numeric zero stays zero; a zero kcal value takes precedence over kJ fallback. Never assume water has zero nutrition solely from its name/category.
- Show the basis and sugars in lookup review. Save an attributed personal food, then explicitly confirm intake. Offer 250/330/500 ml portions and an additional explicit label serving when available. Custom foods can declare either basis; changing a new draft's basis clears values/servings to avoid reinterpreting them. A saved food's basis is immutable; create another food to correct it.

## Minimal necessary forward migration

`20261025184645_liquid_nutrition_basis.sql` adds only two columns: `foods.nutrition_basis` (checked `g`/`ml`, default `g`) and nullable `nutrition_entries.ml_snapshot`. It retains existing legacy `*_per_100g` macro column names for API compatibility; their denominator is now explicitly supplied by the food basis. Existing gram data is not converted or relabeled.

Gram portions retain `{grams}`; liquid portions use `{ml}`, with matching-basis validation in both the server action and SQL. Intake SQL derives trusted totals, nutrient values and unit conversions, stores immutable `basisUnit` with the original snapshot, and records either grams or milliliters. Quantity corrections always use the original basis/servings, even after catalog changes or forged client totals/basis. Old snapshot JSON without `basisUnit` continues to mean grams. Legacy records without a calculation basis retain all their old fields and reject invented recalculation. The planned-meal immutable recipe branch from migration 008 is preserved.

The existing RLS, ownership guards, indexes, grants and invoker-security RPCs remain. A new non-callable trigger rejects volume-only foods in gram-based recipes, including direct writes; the recipe UI excludes them and explains that limitation. Changing a saved food's basis is prohibited, so a catalog edit cannot reinterpret existing recipe ingredients. No recipe density, cooked-yield or mixed-volume recipe feature is introduced.

The migration is necessary to avoid storing liquid quantities in gram fields. Isolated local/native verification precedes production. The production CLI dry run selects **only** `20261025184645_liquid_nutrition_basis.sql`; history contains 001–009 and no copy of the new version. New food basis is NOT NULL with constant default `g`; new volume snapshots are nullable with implicit NULL default. There is no data deletion, backfill, or intake recalculation statement. Trigger replacements retain gram/legacy/planned-meal behavior. Lock and statement timeouts abort a busy migration transaction rather than waiting indefinitely. CLI migration history tracks the new version once; a second dry run after application must select nothing.

The preflight reads production over verified TLS and records counts plus sorted row digests for all 27 application tables, excluding only the two additive fields from comparison. The baseline has 2,121 foods, one nutrition entry, 27 RLS tables and 35 policies. Compare all old fields immediately after migration, before disposable acceptance fixtures are introduced. Require unchanged digests/counts/policies and expected `g`/NULL defaults, plus exactly one migration-history row. Preserve all real records; only runner-owned generated test accounts/data may be removed. The normal application runs after migration; no reset, migration repair, or reseeding is part of release.

## Remaining limits

Ambiguous/incomplete product metadata is deliberately rejected. OFF data remains contributor-supplied and should be checked against the package. There is no automatic density inference or conversion between mass and volume, no inferred water/sugar-free zero, no mixed-unit recipe support, and no automatic personal-food deduplication. The liquid enhancement has not been tested on a physical iPhone; mobile Chromium emulation is not Safari. Production acceptance explicitly enables live OFF checks (no preload/fixtures), including real energy drink `9002490100070`, sugar-free drink `5449000133328`, and verified-zero water `3057640257858`. Incomplete live record `9002490216030` must remain rejected. Provider data can change independently of the app.
